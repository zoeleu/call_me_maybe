How a 0.6B model is made to write valid function calls

The program never asks the model to "answer in JSON". It writes the fixed JSON itself and, at every token, lets the model choose only among the tokens that keep the call valid. Everything below is driven by the project's real code and a real trace of Qwen3-0.6B.

Section 3

The JSON value state machine

Each value is written as ␣<value><end>, where end is , before another parameter or }} after the last one. The state is a pair (phase, matched). A token is allowed only if every character of its text can be fed through _value_step without hitting None. That is how multi-character tokens like "}} or ", are accepted. This page runs a line-for-line JavaScript port of src/decoder.py:35–125.

Tokens, then each character's transition (click a row to see that state)

Why characters, not tokens

Token boundaries are arbitrary: Qwen may write "}} as one token or as " + }}. Checking text character by character accepts every tokenisation the model likes, so it is never pushed into unusual tokens.

Cached tables

_value_table runs all 151,643 token texts through the machine once per (type, end, state) and caches the result, so later steps cost a dictionary lookup. src/decoder.py:361

Length limit

After max_value_tokens (64 in config/prompts.json), only tokens that move to the end phase stay allowed, so a value that keeps going is forced to close. src/decoder.py:350

A second guard after the machine

The machine checks the shape. _parse_value then parses with json.loads, int or float and rejects non-finite numbers, and _check_schema checks the Python type. The output is re-serialised by pydantic, so 007 (accepted by the machine) is written as 7.
